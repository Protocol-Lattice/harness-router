01 · loop

The router is part of the loop.

The important boundary is no longer just a tool interception. Harness Router has an entry point before execution and an observation point after execution. That gives the integration a closed lifecycle: decide → execute → observe → decide again.

harness-router / control flow pre → execute → post → state
01
PRE_DECISION
Inspect the pending action, available tools, cache and routing context.
02
DECIDE
Use cache, fast routing, Jev or escalate to MCTS when needed.
03
EXECUTE
The harness executes the selected tool subject to its own approvals and policies.
04
POST_TOOL_USE
Observe the tool outcome: success, failure and execution context.
05
STATE → NEXT
Feed relevant outcome state into the next pre-decision.
Closed loop: pre_decision → decision → tool → post_tool_use → state → pre_decision
02 · decision

Cheap when obvious.
Search when ambiguous.

Routing is deliberately hierarchical. A known decision should not pay for a model call. An uncertain choice can use Jev, while a downstream workflow can escalate to bounded MCTS. The router therefore spends computation where the decision actually needs it.

01 · CACHE FASTEST

Reuse a compatible previous decision before invoking the decision engine.

02 · ROUTE JEV

Resolve ordinary tool selection with a lightweight policy decision.

03 · MCTS DEEPER

For ambiguous downstream choices, search a side-effect-free state graph.

04 · FEEDBACK POST

Observe the executed tool and make its outcome available to the next decision.

03 · feedback

Execution becomes context.

post_tool_use closes the gap between choosing a tool and knowing what that tool actually did. A successful read, a failed command, or another execution outcome can become part of the context used by the following decision. This is the architectural bridge from routing individual calls toward controlling the sequence of next actions.

pre Decide what should happen next. pending action · tools · cache · routing policy
post Record what happened after execution. outcome · error · result · state transition
Important boundary: Harness Router does not claim ownership of every part of an agent's reasoning. It provides a decision/control-flow layer around tool execution while the host harness retains its own planning, permissions and execution semantics.
$ 06 · Project Hooks

Discover tools. Own the next step.

Choose Codex, Claude Code, ohmypi, Antigravity, or DeepSeek Harness. The integration reads the available tools, then uses Harness Router to precompute and enforce the next tool where the harness allows it.

01 · INSTALL HOOK

Add the project hook

Run the installer in your project root. It adds the integration files and keeps generated state out of Git. Codex, Claude Code, and Antigravity get merged hook settings; ohmypi loads its extension automatically. Antigravity also gets the Harness Router MCP registration.

Choose your provider
Project root · Python 3.11+
curl -fsSL https://raw.githubusercontent.com/Protocol-Lattice/harness-router/main/scripts/install_hook.py \ | python3 - --provider codex

Keeps existing settings and other hooks. Backs up changed files. Safe to run again. View installer ↗ Use --provider all for all five, or --provider both for Codex and Claude Code.

02 · START

Start a fresh Codex session

With harness-router-mcp installed and OPENROUTER_API_KEY exported, start Codex. The startup hook discovers its MCP tool inventory and builds the session catalog.

.codex/hooks.json .codex/hooks/discover_tools.py .codex/hooks/pre_tool_use.py

Start a fresh Claude Code session

With harness-router-mcp installed and OPENROUTER_API_KEY exported, start Claude Code. The startup hook discovers native tools from claude mcp serve and configured MCP tools through the SDK control interface, then publishes the live registry for routing and session commands via HARNESS_ROUTER_TOOL_REGISTRY. Discovery makes no model call.

.claude/settings.json .claude/hooks/discover_tools.py .claude/hooks/pre_tool_use.py

Start ohmypi in your project

With harness-router-mcp installed and OPENROUTER_API_KEY exported, run omp from the project root. It automatically loads .omp/extensions/harness-router.ts; no hook configuration file is needed.

.omp/extensions/harness-router.ts .omp/hooks/pre_tool_use.py .omp/tsconfig.json .omp/package.json .omp/bun.lock

To start with automatic extension discovery disabled, load Harness Router explicitly from the project root:

omp --no-extensions --extension .omp/extensions/harness-router.ts

The installer uses Bun to install the pinned TypeScript dependencies and check the extension automatically. Bun must be on your PATH. To repeat the type check later, run:

cd .omp bun run typecheck

The extension reads the real runtime catalog through pi.getAllTools() and pi.getActiveTools() before each tool_call, including active MCP and extension tools. No separate discovery process or model call. ohmypi hook guide ↗

Start DeepSeek Harness

With harness-router-mcp installed and OPENROUTER_API_KEY exported, install the DeepSeek Harness hook. It uses DeepSeek's supported tools/pre-execute interception point through the @deepseek-ai/dsh-hooks-codex bridge.

.dsh/harness-router-hooks.json .dsh/harness-router.patch.yml .dsh/hooks/hook.py

Start DeepSeek Harness with dsh --patch .dsh/harness-router.patch.yml. The hook fails open if routing or its explicit tool catalog is unavailable. DeepSeek hook guide ↗

Start a fresh Antigravity session

With harness-router-mcp installed and OPENROUTER_API_KEY in Antigravity's environment, restart the project session. The installer registers native PreToolUse and Stop hooks, plus an MCP server exposing both route and route_mcts.

.agents/hooks.json .agents/mcp_config.json .antigravity/hooks/discover_tools.py .antigravity/hooks/pre_tool_use.py

Before each routing check, the hook reads the native and MCP tools exposed to this conversation from the running language server, including their exact names and schemas. Disabled or disconnected MCP tools are filtered out. A failed refresh lets the pending call continue without routing from an old catalog.

Automatic routing starts with route; escalation to route_mcts requires a side-effect-free graph provider. Live discovery uses internal APIs inspected in Antigravity 2.11.0. See the guide for runtime connection overrides and simulator setup. Antigravity hook guide ↗

Behavior

Fail open. Keep approvals.

Each pending tool call uses fast route first. When that decision is uncertain and a side-effect-free graph provider is configured, the hook can escalate to route_mcts. Without a graph provider it never invents an MCTS tree. Same choice, fallback, timeout, or router error lets the original call continue. A different confident choice blocks only that call and asks your agent to re-plan once. Sandbox and approval rules remain untouched.

05 · install

Install the layer.
Keep the harness.

Harness Router is designed to sit beside the existing agent harness rather than replace its authentication, approvals or execution environment.

01 · INSTALL

Install the router

Install the current main branch as an isolated uv tool.

uv tool install --force \ --with 'mcp>=2,<3' \ 'git+https://github.com/Protocol-Lattice/harness-router.git@main'
02 · HOOK

Install a provider hook

Run the project installer and choose the harness you want to integrate.

curl -fsSL https://raw.githubusercontent.com/Protocol-Lattice/harness-router/main/scripts/install_hook.py \ | python3 - --provider codex
03 · RUN

Start a fresh session

The hook discovers the runtime tool context and enters the decision lifecycle.

pre_decision ↓ route / route_mcts ↓ tool ↓ post_tool_use
$ harness-router

Control the next step.

Cache obvious decisions. Route uncertain choices. Observe execution. Feed the outcome into the next decision without taking ownership away from the harness.
